# Phase 8 notes: the extension

**Done when:** it loads unpacked and forges on all three sites. It builds, the manifest is derived
from the catalogue, the panel opens the right anvil for the site you are on, and the three adapters
write into the field each site uses. `pnpm verify` exits 0.

## The split, and why

A browser extension needs a browser, and the paste adapters depend on markup we do not control and
did not write. So the same split as phase 7:

- **`packages/extension`** is everything testable in Node: the manifest, and the adapters as pure
  functions over a `Document`. Twenty tests, in jsdom, against markup shaped like the real thing.
- **`apps/extension`** is the wiring: a service worker, a content script and the panel. Thin.

The manifest is **generated from `HOSTS`**. If it repeated that list by hand the two would drift the
first time a model was added, and the failure would be silent: the extension would simply do
nothing on the new site. A test asserts every host in the catalogue has a match pattern and every
pattern matches a model.

## The panel is a page, deliberately

Every browser API the panel needs goes through `apps/extension/src/bridge.ts`, which falls back when
there is no extension around it. That is not a courtesy: it is what lets Playwright open the panel,
drive it and assert on it like any other page. Ten smoke tests and eight axe checks run against the
real built panel rather than a mock, at 400px and 320px, in both themes.

## What the panel is, and is not

It is not the website in a narrow column. Four hundred pixels is a different brief: open on the
model for the site, ask the questions only you can answer, strike, put the result in that site's own
box, and link to the full workspace for the rest.

It draws **the same generated brief the website draws**. `Brief` and the glossary join moved into a
new **`packages/workbench`**, which the website and the panel both consume, so the form cannot drift
between them. That sharing is the reason section 14 gives for the monorepo, and until this phase it
was a claim rather than a fact.

## The adapters

Three, as section 14 names: Midjourney, ElevenLabs, Suno. Each has a list of selectors from the most
specific the site gives us to the most generic, so a renamed test id falls through to something that
still works rather than failing outright.

Two things they get right that are easy to get wrong:

- **The clipboard first, then the page.** Whatever the adapter does, the prompt is already somewhere
  usable, so a site that changed its markup overnight costs one paste rather than the work.
- **The native value setter.** React keeps its own copy of an input's value and puts it back on the
  next render, so `el.value = text` is undone. The setter on the prototype is the one React's
  plumbing watches. All three of these sites are React apps. It has the most tests of anything here.

An adapter that cannot find its field is **not an error**. A test asserts none of the three
sentences apologises, calls the clipboard a failure, or contains an em dash.

## Deliberate departures

- **No `@crxjs/vite-plugin`.** Section 14 names it. Its job is manifest rewriting and hot reload;
  the manifest here is generated by a unit-tested function, which is better than rewriting, and two
  small Vite configs plus one script replace a long-running beta dependency in the build path.
- **Three permissions and no more.** No `tabs`: the content script tells the panel which site it is
  on, so the panel never asks the browser about your tabs. A test asserts `tabs` and `<all_urls>`
  are absent. Every match pattern is `https://`, so a prompt is never written into a page fetched
  over plain http.
- **The content script carries no catalogue.** It imports the adapters directly rather than the
  package index, which took it from 183 kB to 1.6 kB. It is injected into every matched page, so its
  size is somebody else's page weight: a test fails if it grows past 20 kB.

## Not done

Publishing to a store, which is a registration fee and a decision rather than code. Until then it
loads unpacked from `apps/extension/dist`, which is what section 14 says to do.

The three adapters cannot be tested against the live sites, which need accounts and change without
warning. What is tested is every path through them and the panel around them. When a selector does
break, the fallback is already the tested one.
